# Tuning: hyperopt, backtesting and the meta-learner

> Moved out of the README on 5 Nov 2026, word for word; see "Out of date" at the end of this page for what the 5 Nov check found.

## Hyperopt & backtesting

`HyperoptStatistics.py` uses Optuna to tune each statistical model's parameters per game, driven by `src/Backtester.py`, which evaluates each model using rolling historical validation: for every historical draw, the model is trained only on previous draws and compared against the next real result. A run's best parameters are written to `bestParams_<game>.json` when they pass the champion/challenger gate described below (*The objective and the gate*), together with the served row's score (used by `Predictor.py` at prediction time), including a `modelScores` entry per model (the score of the parameters actually served after the gate - this run's best trial on a replace, the re-scored incumbent on a keep - measured on this run's window and objective, and removed when the row could not be scored this run; keyed by the same display name `Predictor.py` and the report use). Since 26 Oct 2026 a plain run leaves out the `KenoSubsetTuning` strategy (`DEFAULT_STRATEGIES`; `-s` still names it): it is the chain's own last step, `HyperoptStatistics.py -g keno -s KenoSubsetTuning` after `TrainMetaLearner.py` (log `log/kenoSubsetTuning.log`, *The schedule*). Its day table scores the five keno meta-learner artifacts as they are on disk and the weighted vote built from `bestParams_keno.json`, so inside the first job it read both a week old, and the retrain then replaced the artifacts it had just tuned on. The statistical job is 11-13 minutes shorter and the new step takes about a quarter of an hour. `HyperoptEnsemble.py`, which slices the SubsetEnsemble row's keno ticket with the weighted vote's keys when it has none of its own, now reads last weekend's values, and so that the row is served with the slicing it was gated with - not the one the keno step writes after it - it writes the values it scored with as the row's own `subsetEnsembleSubsetMode` / `subsetEnsembleSubsetTemperature`, which `Predictor.py` reads first, and names them in its gate record (`kenoSlicing`). That pin is its own, not a choice made by hand: the next run reads past it to the weighted vote's keys again, so the row follows the weighted vote a weekend behind; keys set by hand are kept.

**The Markov row's two transitions (`markovTransitionMode`, 5 Oct 2026).** The `Markov Model` has had two definitions. From 13 Feb 2025 it learned one table over the whole game, from each number to the next number inside the same sorted draw - the shape of a ticket, where the gaps between its numbers come from, not time. On 3 Feb 2026 ("updated markov to learn transition t+1") that became one table per column, from the number in a column in the previous draw(s) to the number in the same column in the next draw, the definition the Backtester, the tuner and the meta-learners have scored since; the `MarkovBayesian Model` and `MarkovBayesianEnhanched Model` rows still learn the within-draw table. Both are now the row's knob: `column` (the default, and what every `bestParams_<game>.json` serves until its tuner says otherwise) or `within` (the 2025 ticket: a tempered successor from the within-draw table for the start state and then for every number of the last draw, up to the draw's size, the ticket filled from the last number's successors blended with the game's frequencies, then pair affinity, then the range; three things differ from 2025: the softmax is today's log-space one; the bonus and star columns, which rode along in the 2025 table as the last step of every draw, stay out - lotto drops its bonus and the special columns are modelled apart; and, since 13 Oct 2026, the chain has a start state (below), which the 2025 table did not). The statistical tuner offers the choice for the set games and scores both on the same days under the gate, so the Saturday chain of 10 Oct 2026 is the first fair comparison; the positional games have only the column path (a sorted set of distinct digits cannot express pick3's order or Joker+'s repeats) and the model says so once if asked otherwise. For the record, what the stored day files say, each ticket's first draw-size numbers against the drawn main numbers (the 2025 tickets of lotto, euromillions, eurodreams and vikinglotto were sorted sevens - mains and bonus or stars from one chain - so their highest number is dropped; the History ranking, which counts lotto's whole ticket, has 0.78 and 0.81 for the two eras) - the live draws of 12 Nov 2025 to 2 Feb 2026 (the within-draw row, read from git as the files were then; today's store holds the same Markov tickets for every one of them) against 4 Feb to 5 Oct 2026 (the column row): keno 6.04 hits per draw over 82 draws against 5.53 over 243 (a random 20-number ticket 5.71; the column tickets carried 55 numbers above 70 and six duplicates over those 243 draws - the 1-80 range of the paragraph above at work - so their own fair baseline is 5.63), lotto 0.65 over 23 against 0.79 over 70 (random 0.80), euromillions 0.48 against 0.46 (random 0.50), eurodreams 0.88 over 24 against 0.63 over 27 (random 0.90), vikinglotto 0.50 over 10 against 0.83 over 35 (random 0.75). The keno figure is where the memory of good hit rates comes from: it is 1.7 standard errors above chance, the best of eight rows scores 6.14 on a shuffled keno history, and the two rows that still use the within-draw table sit at 5.84 and 5.54 over 330 draws - chance. The knob exists so that the tuner, not that table, answers the question. **13 Oct 2026:** the first Saturday chain chose `within` for lotto and euromillions, on margins of 0.4 and 0.6 standard errors (in lotto the best column trial scored 0.8140 against within's 0.8148 - a tie in all but name), kept column for eurodreams and vikinglotto, and for keno sampled within only, every trial below both column references. The within chain as built on 5 Oct never played number 1, and only the frequency fill gave it a score - about a tenth of its fair share under the served `log` blend, and nothing in the vote count, since its tickets never held it: the smallest number of a sorted draw is nobody's successor. It now reads every draw as a chain from a start state (`Markov.WITHIN_START`) to its smallest number and on, so the start state's table is the distribution of the draw's smallest number, the ticket draws its first pick from it and stops at the draw's size, and number 1 is scored and played at about its share; the lotto and euromillions within rows tuned on 10 Oct are re-scored like for like by the next gate.

`HyperoptDeepLearning.py` tunes the deep learning models per game and per model type (`lstm_model`, `tcn_model`, `unified_lstm_tcn_model`, `unified_lstm_gru_tcn_model`, plus the research types `transformer_model`, `gnn_model`, `autoencoder_model`), each in its own Optuna study writing prefixed keys, scored primarily on held-out `val_loss` with real-draw profit as a small tie-breaker. It is **not** in the weekly `runHyperopt.sh` (DL training is the time/memory bottleneck); run it manually, and use `--models` to tune only what you need - e.g. `python3 HyperoptDeepLearning.py -g pick3 --models transformer_model,gnn_model,autoencoder_model` tunes just the cheap research rows without paying for LSTM/unified studies. `autoencoder_labelSmoothing` is pinned to 0 by its search space on purpose (the reconstruction NLL doubles as the anomaly signal).

`HyperoptQuantum.py` tunes the two quantum meta-learners and their classical control (`quantumKernel_*` / `quantumVqc_*` / `classicalSvm_*` keys): per game it collects the backtest score table once (`-d`, default 300 days, the same window `TrainMetaLearner.py` uses), then runs three Optuna studies (`<game>-quantum_kernel`, `<game>-quantum_vqc`, `<game>-classical_svm`) against a chronological 75/25 **day** split - the variant is fitted (scaler/PCA included) on the early portion only and scored on the held-out days by mean per-day hits of the top-`draw_size` ranked numbers (the ticket-level metric that is actually played), with AUC as a +0.01 tie-breaker. Kernel and RBF-control trials run in under a second; VQC trials in seconds to half a minute. The collected table is persisted to `data/hyperOptCache/meta_score_table_<game>.joblib` and reused by `TrainMetaLearner.py` minutes later in the same weekly run (strictly validated: any new draw or changed base-model param recollects), so the pipeline's most expensive stage runs once, not twice. Each run judges its own trials only - cross-week trial scores were measured on different holdout windows and are not comparable - and, since 14 Oct 2026, through the champion/challenger gate like the statistical, boosting and RL tuners (`src/TuningGate.py`; `--gate-margin`, `--no-gate`): a run's best trial is written only if it beats the served parameters and the untuned defaults (`QUANTUM_DEFAULTS`: the values `src/QuantumModels.py` serves when the keys are absent, with 0.25 standing in for sklearn's `"scale"` gamma of the RBF control), both re-scored on the run's holdout by the same objective; the defaults are served back when they beat both (by the same margin); the record is `tuningGate["QuantumMetaLearner Model" | "QuantumVQC Model" | "ClassicalSVM Model"]` with the holdout hits (or payout) and AUC behind each score. Until then this run's best trial was written as it was (`HyperoptDeepLearning.py` and `HyperoptEnsemble.py` still write without a gate). The gate judges by this tuner's own objective and by a margin of one standard error of the challenger's score, which both objectives carry since the same day (the Pick3/Joker+ one replaced the raw payout that evening: one pair had moved production's 56-day holdout mean by 0.9 a day). Note: the quantum and control rows' Keno subset mode/temperature keys (`quantumMetaLearnerSubset*`, `quantumVqcSubset*`, `classicalSvmSubset*`) are not tuned here: since 15 Oct 2026 the Keno subset tuning (`KenoSubsetTuning`) searches them with the classical meta rows' - until then they kept the softmax/0.5 defaults - and since 26 Oct 2026 it is the chain's own last step, after the retrain (`HyperoptStatistics.py -g keno -s KenoSubsetTuning`). Runs in the weekly `runHyperopt.sh` after `HyperoptRLTicket.py` and **before** `TrainMetaLearner.py`, so the weekly retrain always trains the quantum artifacts on freshly tuned params. Pick3 and Joker+ are tuned positionally on their own table (`meta_position_table_<game>.joblib`): since 14 Oct 2026 the objective is the statistical tuner's positional score (`TuningScore.score_bets_by_day(positional=True)`: the lower bound over the held-out days of the argmax ticket's hits - Pick3's digits in the right slot, Joker+'s paid runs L + R as the Backtester counts them - plus 0.001 x the capped-profit bound as the tie-breaker; the raw payout per day and the top-1 accuracy stay on the record), in fresh studies (`<game>-<variant>_slot_bound`) because the old ones' values were raw payouts - the mean real payout of the ticket (+0.01 x top-1 accuracy), which one pair (+46 against -4 on a miss) in a 56-day holdout moved by 0.9 a day. The market games are positional too (an instrument per slot) and keep their objective, the mean per day of the fixed rule's P&L in bin space (`Helpers.market_ticket_profit`, bounded by a day's move) + 0.01 x top-1 accuracy, in their existing studies. Every quantum challenger must also win by a margin in standard errors of its own score (`--gate-se-margin`: 2.5 by default since 27 Oct 2026, 1 until then - *The margins, per tuner*): the Pick3/Joker+ score carries it through TuningScore, the hits and P&L scores as the standard error of the per-day values.

`HyperoptRLTicket.py` tunes the RL Ticket Model (`rlTicketLearningRate/Epochs/SamplesPerDay/TrainDays`) with an honest walk-forward over the game's own stored day JSONs: each evaluated day is re-predicted with `cutoffDate` set to that day (training sees only strictly earlier days) and scored against its real draw by the tuners' shared lower bound (`rl_row_material` + `TuningScore.score_bets_by_day`, since 13 Oct 2026): Keno's served subsets (enabled sizes only) as (profit, size) bets, each capped at 20 EUR and measured against a fair ticket of its size; Pick3 by positional slot hits, with the capped profit as a 0.001 tie-breaker; main-ticket hits elsewhere. A run's best trial is written only through the champion/challenger gate (`--gate-margin`, `--gate-se-margin`, `--gate-revert-margin`, `--no-gate`), which compares it with the served knobs and the untuned `RL_TICKET_DEFAULTS`, both re-scored on the same days, and writes the defaults back when they beat both (since 27 Oct 2026 a challenger must win by one standard error of its score and the defaults come back by any gain - *The margins, per tuner*); the studies are `<game>-rl_ticket_gated` and the record is `tuningGate["RL Ticket Model"]`. Until 13 Oct 2026 trials were scored by the plain uncapped mean per day and the study's all-time best was written without a gate. Pure numpy, minutes per game, so unlike the DL tuner it *is* part of the weekly `runHyperopt.sh` (after `HyperoptBoost.py`, sharing the same `process.lock`). Per-trial policies live in `data/hyperOptCache/rl_model`; the live `data/models/rl_model` policy is never touched by tuning.

`HyperoptEnsemble.py` selects the rows of the `SubsetEnsemble Model` (roadmap item 2). Like the RL tuner it works on the stored day JSONs rather than the Backtester - the only place where every tracked row (statistical, boosting, deep learning, meta-learner, quantum) exists side by side for the same draws, tuned as it was at the time. Per game: the candidate rows are those present on at least 80% of the last `--days` (default 120) scoreable days *and* on at least three of the last five (a row the pipeline no longer emits cannot be a member of a served row - the `LSTM Base Model` row stopped appearing in mid-August 2026, still covered 79 of 87 lotto days, got selected, and the served row was then skipped daily for a missing member), minus the two vote rows and the RL row (appended after the vote, so never available to it); a combination is one include flag per candidate plus `subsetEnsembleWeighted` (vote with the `modelScores` weights or count every member once); each combination votes the selected rows with `Helpers.build_vote_ensemble_predictions` on every day all of them exist and is scored like the report scores served rows - profit per bet over the enabled Keno subsets, main-ticket hits elsewhere. One evaluation takes 2-20 ms in-process, so **the space is enumerated exhaustively** whenever 2^rows x 2 fits the evaluation budget (`-t`, default 16384 - twelve candidate rows); beyond that a deterministic local search runs (hill-climbing over single flag toggles from the all-in vote, weighted and flat, and from the best pair), every combination evaluated once. The evaluated combinations are written into the game's Optuna study as completed trials, best first (`--record`, default the best 256; writing a trial to SQLite is ~70 ms, the search itself under a second), so `db.sqlite3` (and the Optuna dashboard, when started by hand) hold this run's ranking without duplicates. This replaced a first version that drove the search with Optuna's TPE through the process-per-trial runner: sampling boolean flags independently, TPE collapses onto its mode and re-proposes the same subset trial after trial (a production run spent 162 trials on 37 distinct subsets, one of them 62 times), and the runner spent ~2 s launching each 5 ms evaluation. A subset is scored only on the days all of its members exist, and it counts only when that is at least 60% of the window - every scored subset then sits on nearly the same draws, which is what makes their values comparable. This rule came out of testing: with a looser floor the search found a six-row subset that happened to break even on the ten days its members coexisted and ranked it above every subset that lost keno's house edge over 300 days - with thousands of subsets in the space such a fluke is always there to be found. The consequence is that the weeks-old boosting/meta-learner/quantum rows are not candidates yet at the default window; they join automatically as they age into it, or right away with a shorter window (`--days 60`), at the price of fewer draws for everyone. The value of a subset is a lower confidence bound on the per-day score, mean − std/√days (`--confidence-penalty`, default 1; 0 gives the plain mean), which mildly favours the subsets covering more of the window; a subset of fewer than two rows is not a subset. The all-in weighted vote (the `WeightedEnsemble Model` over the same rows) is always among the evaluated combinations and is printed next to the winner, so the log shows what the selection gained. Only the derived selection is written to `bestParams_<game>.json` (`subsetEnsembleModels`, `subsetEnsembleWeighted`, `subsetEnsembleObjective`, `subsetEnsembleMean`, `subsetEnsembleTunedOn` - the latter with the window, the number of candidates and combinations, the search kind and, since 15 Oct 2026, the gate's `decision`) - never the include flags, and never the row's own score into `modelScores`. The selection is this run's best when it passes the gate below (otherwise what is served stays, or the plain vote is served back); older runs' trials stay in the study as history (user attribute `run`), but were scored on a different window and are not compared. Runs in `runHyperopt.sh` after `HyperoptRLTicket.py`. Since 4 Oct 2026 the two market games are tuned too, with the fixed rule in bin space as the day's score (`Helpers.market_ticket_profit`). The positional games take the per-slot vote branch (`Helpers.build_positional_vote_predictions`, the recipe the served rows use): pick3 is scored with `pick3_ticket_profit` (profit per bet of the cumulative four-bet ticket), Joker+ with `jokerplus_ticket_profit` and only when `useJokerplusEnsemble` is set, and because their payouts are sparse (most days every subset loses the stake) the value adds 0.01 x the mean share of slots the ticket got right as a tie-breaker. Honest caveat: the selection is made on the rows' stored real-life history, so on the day it is written the subset is in-sample by construction - what makes it a fair row is that its tracked results accrue only from then on, out of sample, next to every other row. Since 15 Oct 2026 the selection goes through the champion/challenger gate like every other tuner of the chain (`src/TuningGate.py`; `--gate-margin`, `--gate-se-margin` 1 by default, `--gate-revert-margin` 0 since 27 Oct 2026, `--no-gate`): this run's best combination is written only if it beats the served selection and the plain vote - every candidate row, weighted, the `WeightedEnsemble Model` over the same rows - both re-scored on this run's days by the same evaluation, and by one standard error of its own score; the plain vote is served back when it beats both (since 27 Oct 2026 by any gain: it is a fixed reference, not picked from trials), and the record is `tuningGate["SubsetEnsemble Model"]` (with the candidates of the run). A served selection that cannot be served - a member the pipeline no longer emits, or nothing written yet - is scored as nothing, so the run writes the challenger or the plain vote and the row is revived (the review caught a first draft scoring the selection minus the missing member, a proxy the challenger could never beat by the margin). On keno and pick3 the standard error of a selection's score is larger than the spread between any two selections (0.67 and 1.06 against 0.42 and 0.15 on 15 Oct), so there the gate keeps what is served unless it cannot be served or the plain vote beats it by that much. Until then this run's best combination was written as it was. **Since 25 Oct 2026** a weighted combination one member outweighs is infeasible like a one-row subset, so every value in the study is an ensemble's (its flat version stays in the search), and a served selection in that state is scored as nothing with a note naming the member, like a dead one; on the markets the tie-break and the one-voter rule apply as served, and XGBoost + LightGBM alone are infeasible. The gate's record gains `effectiveMembers` (the members that can still change the served selection's ticket under this run's weights) and `weightedEqualsFlat` (weighted, but every member weighs 1.0 - unscored, or scored at the minimum - so "weighted" is the flat vote: crypto, shares and sharesweek under `modelScores` that day). On the market games, where `modelScores` cover only the four statistical rows, the vote is now weighted by each candidate's own score: `member_scores` scores its stored ticket as a vote of one with this run's objective, lower bound and window, `subset_weights` maps those values to [1, 2] like `modelScores`, and every combination of the run, the gate's references included, is scored under them. They are written as `subsetEnsembleWeights` whatever the gate decides (it scored the served selection under them too), the raw values as the record's `memberScores`; the lotteries keep `modelScores` and get neither. Two caveats: the weights come from the window the selection is made on, so they are as in-sample on the day they are written as the selection is (simulated on that day's files, they alone lifted crypto's served selection from -0.38 to -0.08, within one standard error of the best challenger, so the gate would keep it); and with a weight per member any weighted pair whose two weights differ is one member's ticket, so only flat pairs stay in the market search (108 infeasible combinations on crypto, against 41). The market plain vote the gate compares against is weighted the same way, so it is no longer exactly the served `WeightedEnsemble Model`, which keeps `modelScores`.

`HyperoptBoost.py` does the same job for the boosting model, and is now a direct mirror of `HyperoptStatistics.py` rather than the separate legacy pipeline it used to be. Two run-time guards keep it inside a weekend: **CatBoost's tree depth is searched over 1-7** (its symmetric trees cost 2^depth - measured median minutes per trial by depth: 1-6 → 1-4, 8 → 24, 10 → 64, with single trials up to 12 hours, while XGBoost/LightGBM keep the full 1-10 range), and **every trial has a wall-clock budget** (`--trial-timeout`, default 1200 s) after which the Backtester terminates its worker pool and Optuna records the trial as pruned. Every trial is also stamped with a monotone **fit-cost proxy** (estimators x window, x 2^depth for CatBoost), and a later configuration at least as expensive as one that already hit the budget is skipped immediately as a predicted timeout (recorded as pruned, not counted toward `--trials`). This matters because Optuna's TPE sampler proposes its first ten trials at random and on keno roughly half the search space cannot finish one refit block inside the budget: the per-position formulation trains 20 multiclass models over 80 numbers, and XGBoost/LightGBM grow one tree per class per round, so keno LightGBM burned six 20-minute timeouts in its first seven trials, each more expensive than the one that finished. The gate only trusts timeouts recorded under the same budget tag (machine, window, cadence, budget), so stronger hardware or a larger budget starts from a clean slate. Two further levers attack the real cost driver - refitting a boosted ensemble for each evaluated day (90 by default since September 2026, 31 before): a **refit cadence** (`--refit-every`, default: the window over five blocks - 7 at 31 days, 18 at 90 - so a trial keeps the shape the budget, thread count and parallelism below were calibrated for) trains one fit per block of consecutive days (block-aligned on the data *before* the oldest day of the block, so it is conservative, never leaky; every day still builds its own prediction features, and the fit cache keeps the main and special-column fits side by side) - identical for every trial, so the ranking is untouched while production keeps refitting daily. Measured on eurodreams CatBoostMultiLabel (2 trials x 21 days): 7.5 min at cadence 1 -> 66 s at cadence 7, with objective values in the same range. Threads are per library, from measurement: CatBoost scales (one fit: 4 threads = 3.1x) and gets the cores its fewer workers leave free; XGBoost/LightGBM stay single-threaded (giving XGBoost 5 threads made a study 5x *slower*), and the tuner pins OpenBLAS/OpenMP to one thread per process because every worker otherwise inherited a 16-thread BLAS pool whose spin-waiting cost ~10 cores of pure overhead per fit; and **conservative pruning** (`--prune-percentile`, default 75, 0 disables): the partial score after each scored day is reported to an Optuna `PercentilePruner` that stops only a trial whose best partial so far is in the bottom quartile, after half the scored days and only once five trials have completed - pruned trials are recorded as pruned, never as bad scores. Optuna's percentile is the share of trials *kept* (on a maximising study it compares with the (100 − p)th percentile), so the default of 25 used until 26 Oct 2026 stopped all but the top quarter: on 24 Oct 224 trials were pruned against 314 completed of 540, and 7 of the 36 studies finished three or fewer. The fix costs at most +0.46 to +0.65 h on the ~10.4 h boosting run, for up to 479 completed trials. Since 30 Oct 2026 the pruner is the tuner's own `CheckpointPruner`: a trial is judged only at half and at three quarters of the scored days, on its partial score *at* that day (Optuna's pruner judged its best partial so far, which a lucky first stretch kept up after it faded), and only against the completed trials of this run - the study is reused every weekend, and last weeks' trials, fitted on another window, no longer set the bar. **Trials of one study run in parallel processes** (`--parallel-trials`, default auto = the cores the per-trial workers leave idle: with 5 refit blocks on 15 cores, 3 trials at a time - the block count the default cadence keeps at any window of 29 days or more; below that the 7-day floor gives fewer blocks and more concurrent trials) for the XGBoost/LightGBM strategies, whose single-threaded fits used 5 of 15 cores; CatBoost keeps one trial at a time and the idle cores as fit threads. A further trial only launches while the machine keeps `--memory-reserve-gb` (default 2) available after it, with the expected footprint measured on the trials already running, and under 1 GB available the youngest trial is stopped and recorded as pruned rather than inviting the OOM killer. Each trial runs in its own process (the Backtester passes worker state through a module global, so two trials cannot share one), which also means a crashing trial no longer aborts the remaining strategies of a game, and trials left RUNNING by a killed run are marked failed when the study is reopened; the sampler runs with `constant_liar` so concurrent trials do not sample the same neighbourhood. Honest note: with a refit cadence above 1 all blocks fit concurrently, so pruning saves little compute (0.79 trial-hours on 24 Oct 2026; it mainly pays off at cadence 1); it is kept because it is free and protects the cadence-1 path. CatBoost's `border_count` (split candidates per feature) is exposed as a knob - `--catboost-border-count` (default 254, CatBoost's own), written to `bestParams_<game>.json` as `catBoostBorderCount`/`catBoostMlBorderCount` so `Predictor.py` serves the same value - for experimentation only: measured on this data (integer features with at most 50 distinct values) 32 vs 254 made no difference in either fit time (1014 s vs 1016 s for a 50-classifier multi-label fit) or ranking (Spearman 1.0), so the default is left untouched. Concretely: it evaluates through `src/Backtester.py` (one Optuna study per game+strategy, `load_if_exists=True`, walk-forward over the last `--days` draws) instead of the old rebuild-a-JSON-cache-and-total-the-profit loop; scores trials with the shared `score_from_summary` (since September 2026 the capped, lower-bound objective of `src/TuningScore.py` - see *The objective and the gate* below; before that profit per bet where a payout table exists, avg hits otherwise) rather than raw total profit; bets the game's served Keno subset sizes (the global `use_<n>` flags, as `Predictor.getKenoSubsetSizes` does) rather than the per-model inclusion mask it used to search; and merges its results into `bestParams_<game>.json` including a `modelScores["XGBoost Model"]` entry, so the boosting model's vote is weighted in `WeightedEnsemble Model` like every other model's. Its `STRATEGIES` / `STRATEGY_DISPLAY_NAMES` tables have the same shape as the statistical ones, so adding a second boosting method (LightGBM, CatBoost) is a one-entry change. The old version could not run at all: it still imported `src/LSTM_ARIMA_Model.py`, `src/RefinemePrediction.py` and `src/TopPrediction.py`, none of which exist in the repo any more.

**The objective and the gate (`src/TuningScore.py`, `src/TuningGate.py`) - September 2026.** Two findings from the served parameters of that month changed how the statistical and boosting tuners score and write. First, the objective. Until then a trial's value was its raw profit per bet over a 31-day window (average hits where a game has no payout table), and on 31 days that number is decided by whether one jackpot-tier payout fell inside the window: the keno LightGBM parameters served from 10 Sept scored 5.0 per bet, of which one draw - a 6/6 with its nested 5/5, +348 EUR - was everything and the other 60 bets lost 38 EUR; the pick3 XGBoost and CatBoost winners were single straights (+756 and +676 EUR) on windows that otherwise lost, and the pick3 statistical studies' best values (21 and 42 per bet) are one and two straights. Optuna's per-day intermediate values show it directly: the cumulative score of each of these trials was negative for most of the window and jumped on one day. The repeat-and-average per trial the tuners once had (three repeats in the original `Hyperopt.py`, a mean-minus-std variant in August 2025 that was reverted a week later) would not have helped - the Backtester is seeded per day, so a repeat returns the same number; the luck is in the draws of the window, not in the model's randomness. Trials are now scored by a **lower confidence bound over the days** (mean − std/√days, the estimator `HyperoptEnsemble.py` already used): for keno the per-day profit per bet with every single bet's profit **capped at the lucky-strike threshold (20 EUR net)**, so a jackpot counts as one good bet and the 1-10 EUR tiers keep their value; for the positional games the per-day **slot hits**, which every draw informs - pick3's digits in the right slot, Joker+'s leading and trailing runs; for pick3 counted by `TuningScore` from the drawn-order ticket and draw the Backtester stores, because the Backtester's own pick3 `_hits` column is the historical *set* count that scores a right digit in the wrong slot (a box) like a straight; for Joker+ the `_hits` column, already L + R runs - with the capped profit bound as a 0.001-weighted tie-breaker - almost every pick3 window is a flat loss once a straight is capped, so profit alone would rank noise; for the games without a payout table the hits bound. The pruning callback scores the finished days with the same function, so partial and final values agree. The raw profit per bet and the number of lucky strikes travel with every trial as the user attribute `tuning`. The default window is **90 draws** (`-d`, was 31) for both tuners. For the boosting tuner the refit cadence scales with it (five blocks at any window of 29 days or more, see above), so a boosting trial's cost, its 20-minute budget and the trial parallelism are unchanged and its run grows only by the reference evaluations, up to two backtests per strategy and game. The statistical tuner has no cadence: each of its trials, and the Keno subset-tuning precompute (whose boosting row refits once a week since 13 Oct 2026, below), backtests every day of the window from scratch over the 15 workers, so both take roughly twice as long as at 31 days - seconds per trial still, and the precompute is now bounded at three trial budgets (an hour), beyond which the row is skipped for that run. Second, the write. Every run used to write `study.best_params` - the best trial the study had *ever* seen - which with the old objective was the trial that caught the biggest payout, kept until a later window happened to beat it (the keno 5.0 was never approached again: 2.13, 1.26). Now **this run's best completed trial is the challenger**, and it replaces the served parameters only if it beats **the incumbent** (the parameters in `bestParams_<game>.json`, re-scored on this run's window with this run's objective) **and the untuned defaults** (what `Predictor.py` serves when the keys are missing - `src/BoostingBase.py`'s table for the boosting rows, `HyperoptStatistics.SERVED_DEFAULTS` for the statistical ones), by `--gate-margin` (default 0; since 27 Oct 2026 also by one standard error of the challenger's score - *The margins, per tuner* below). A trial without a finite score (a backtest that produced nothing) is never a challenger, gate or no gate. When the challenger does not beat the untuned defaults and either the defaults or the challenger beat the incumbent (both by the margin; the second case since 13 Oct 2026, when the boosting margin became one standard error - without it a challenger more than one standard error above the incumbent but not above the defaults kept the incumbent, the lowest of the three: euromillions XGBoost and LightGBMMultiLabel and pick3 LightGBM on the 10 Oct scores) - an exact tie with the defaults included, since 13 Oct 2026: until then an exact tie of the run's best trial with the default kept an incumbent worse than both (in five of the six cases parameters far from the default that score exactly what it scores - the objective is flat there; once, vikinglotto LaplaceMonteCarlo on 10 Oct, the sampler re-drawing the default's 900 simulations), three rows on each of 3 and 10 Oct 2026 - the defaults are written back and the row is reverted - the first production run (26 Sept 2026) found three such rows, e.g. lotto LaplaceMonteCarlo's served parameters at 0.77 against the code default's 0.82. The references are scored by the strategy's own Optuna objective driven by an `optuna.trial.FixedTrial`, so the incumbent goes through exactly the code that scored the trials, each in a forked child (`HyperoptRunner.run_isolated`) because the coordinator must never run a fit itself before forking the next study's trials. A reference that cannot be scored (timeout, error) cannot block, and says so. Every decision is recorded under `bestParams_<game>.json["tuningGate"][row]` - challenger, incumbent and default scores, each one's diagnostics (raw profit per bet, lucky strikes, days), the window, the study's all-time best for context - and `modelScores` carries the score of what is actually served; a row the gate could not score this run loses its old raw-profit entry rather than keeping a weight measured on another scale. `--no-gate` writes the run's best without the comparison; nothing writes the study's all-time best any more. Two additions of 13 Oct 2026: the boosting tuner's challenger must also win by **one standard error of its own score** (`--gate-se-margin`, default 1; `TuningScore` reports the score's `score_se`, the standard error over the days of the series it bounds, and `TuningGate.challenge(se_margin=)` uses the larger of the two margins) - its winners of 3 Oct outside keno (whose scores moved to the fair-ticket scale) lost 0.07 on average when re-scored a week later, because a boosting fit moves with every new draw through its refit blocks, and 11 of its 20 replacements outside keno on 10 Oct had won by less than that; and the RL ticket studies of the lottery games (`HyperoptRLTicket.tune_ticket`) are scored by the same capped lower bound - keno's subsets against a fair ticket of each size, pick3 as the positional slot hits with the capped profit as a tie-breaker, the other games by hits - and go through the same gate in fresh studies (`<game>-rl_ticket_gated`); until then they wrote the study's all-time best of an uncapped mean per day, which for keno was a 13 Sep trial on the 1-80 game with one ticket size and for pick3 one 500 EUR straight. The Keno subset-tuning strategy uses the same capped bound. Two honest notes: a robust objective ranks candidates, it does not make them good - on the September data every keno and pick3 trial's bound is negative, as a fair ticket's would be; and the per-model Keno subset flags the tuners used to search (`lightgbm_use_5`, `markov_use_6`, ...) were written to the file but never read at serve time - `Predictor.getKenoSubsetSizes` uses the global `use_<n>` flags for every row - so a trial's value depended on ticket sizes that never reached production, and the gate would have compared unlike tickets. Trials and references now bet the served sizes (`served_keno_subsets`); the stale per-model keys in older files are ignored. The Keno subset-tuning precompute, the one step no trial budget reaches, is bounded at three trial budgets and the row is skipped for the run when it does not finish. Since 26 Oct 2026 no score in this paragraph counts a lockbox day - not the trials, the references, the standard error behind a margin, `modelScores` or the Keno day table - and every gate record carries `lockbox_days_withheld` next to `window_days` (*Lockbox period*).

**The margins, per tuner (27 Oct 2026).** A gain of 0 let noise through every week: on 24 Oct the statistical tuner replaced 30 of its 73 rows, every one by less than one standard error of its own score (median 0.23 SE, largest 0.86; four with the incumbent's very hit mean). Every tuner now sets the challenger's margin in standard errors of the challenger's own score (`TuningGate.challenge(se_margin=k)`, the larger of that and `--gate-margin`), and the revert to the untuned defaults has a margin of its own (`revert_margin`; `None` keeps the challenger's); every gate record carries `margin_se` (the k asked for) and `revert_margin` (the margin used). Per tuner: **statistical** (every strategy, GARCH and Regime HMM, and `KenoSubsetTuning`, which runs the same script) k = 1 (`--gate-se-margin`; 0 is the old any-gain rule) and the revert by any gain (`--gate-revert-margin`, default 0); **RL ticket and RL position** the same, with the same flags; **ensemble** k = 1 as before, the plain vote served back by any gain; **quantum** k = 2.5 (was 1), the revert keeping the margin - a single fit's score moves about 0.9 SE with its seed alone, the defaults drifted 1.28 SE in a week, and the fifteen replacements of 18 Oct lost a median 1.41 SE on 25 Oct; at 2.5 a fair-game simulation replaces 2-5% of rows a week, against 34-46% at 1 (no refit confirmation: the owner's choice, zero cost); **boosting** unchanged (k = 1, the revert at the margin). **The market rows (October 2026, roadmap item 4 M4).** The `Garch` and `RegimeHmm` strategies tune `src/MarketModels.py`'s rows for `crypto` and `shares` only (`garch*` / `regimeHmm*` keys), through the same studies, gate and record as the rows above, with one difference in the objective: a trial is scored by the **lower bound of the per-day mean log-score** of the probability the row gave the bin that happened (`TuningScore.score_rows(..., proper=True)` over the per-slot probabilities the Backtester collects, floored at the rows' `1e-4`; uniform scores log(1/10) = -2.303), because hit rate is not a proper score and a near-one-hot forecast games it. Details and the search space in roadmap item 4, *M4*.

**Shared run machinery - `src/HyperoptRunner.py`.** The process-per-trial coordinator described above is one module used by every tuner whose trials are expensive (`HyperoptEnsemble.py` evaluates in-process: at 2-20 ms per subset the coordinator's launch overhead would dominate, and its study is written as a ranking instead), so the same guarantees hold across `runHyperopt.sh`: trials of one study run in their own forked processes, in parallel where the objective is single-threaded and the memory gate allows; a crashing trial is marked failed instead of aborting the game's remaining strategies; Ctrl+C or `kill` of the coordinator tears down every trial process with its workers (and the trial processes die with the parent); trials left `RUNNING` by a killed run are marked failed on the next start; the sampler runs with `constant_liar` whenever trials run concurrently. Per tuner: `HyperoptStatistics.py` keeps one trial at a time (the Backtester already spreads each trial's days over every core) but gains the wall-clock budget (`--trial-timeout`, default 1200 s) and prewarms the Keno subset-tuning precompute in the parent so the trial processes inherit it instead of rebuilding it (43 min in production); `HyperoptRLTicket.py` runs one trial per core (`--parallel-trials`, auto) with a scratch policy directory per trial and BLAS pinned to one thread; `HyperoptQuantum.py` does the same on top of the once-collected score table, with a 1800 s deadline per trial (`--trial-timeout`); `HyperoptDeepLearning.py` stays GPU-serial in its spawned child but that child now has a budget too (`--trial-timeout`, default 2 h - a hung trial once had to be found and killed by hand) and stale trials are cleaned at study open. Operational note: `log/hyperopt*.log` is written only when a tuner is started through `runHyperopt.sh`; a run started by hand from a terminal logs to that terminal, and the Optuna `db.sqlite3` trial timestamps are the reliable progress record either way. `runHyperopt.sh` itself first waits (up to 6 h, noted in `hyperoptStatistics.log`) for the daily predictor to release `process.lock` instead of letting each tuner exit on a live lock - with the deep learning rows back in the daily run, a long Saturday run would otherwise silently skip the week's tuning.

## Training the meta-learner (`TrainMetaLearner.py`)

Trains both `MetaLearner Model` and `MetaLearnerV2 Model` per game:

```python
python3 TrainMetaLearner.py --games lotto,keno --days 300
```

For each game, it instantiates the 8 base models using that game's already-tuned `bestParams_<game>.json`, backtests them once with `collect_scores=True` over the last `--days` draws, and builds a (day, number) $\to$ [each model's score, actual-drawn label] training table across the game's full number range — reused for every variant (the two classical rows, the two quantum rows and the quantum kernel's classical control, see *Quantum-assisted research*), so the expensive backtest runs once. It trains `LogisticRegression(class_weight="balanced")` for `MetaLearner Model` and `GradientBoostingClassifier` (class balance via `sample_weight`, since it has no `class_weight`) for `MetaLearnerV2 Model` — each evaluated on a walk-forward holdout split (last 20% of days) and, since 28 Sept 2026, reported with per-number **calibration and ranking metrics** (`src/Calibration.py`: Brier and log-loss against their base-rate values, AUC, ten reliability bins with the expected-calibration error, and the top-`draw_size` hits per day of the holdout against chance - the ticket-level number the History ranking uses; per-slot top-1 accuracy and the argmax-ticket profit for the positional games) instead of a printed accuracy line. The metrics are stored in every artifact under `metrics`, next to `trained_at`, the resolved `params` and, since 28 Sept 2026, `versions` - the Python, numpy, scikit-learn and joblib the artifact was written with, because a pickled model is only as loadable as the library that wrote it and a metric that moved between two weeks reads differently when the library moved too (for the special-column games - Euromillions, EuroDreams, VikingLotto and Joker+ - the special column's report is nested as `metrics.special` and duplicated as a top-level `special_metrics`; lotto, keno and pick3 artifacts have no `special_metrics` key) and in `data/models/<game>/meta_learner_metrics.json` (with the same `versions`), so one week reads against the last - this file is the durable record of the comparison between the meta-learner variants that the quantum track asked for. A malformed `lockbox.json` stops the trainer and the quantum tuner before any backtest is spent; the row tuners go on without it after one warning that the run is not lockbox-safe. The **lockbox** (`lockbox.json` at the repository root, `src/Lockbox.py`, README *Lockbox period*) is enforced here and in `HyperoptQuantum.py`: the declared period's days leave the table before any split or fit, and `--lockbox-report` scores the freshly fitted artifacts on them once, writing `data/models/<game>/lockbox_report.json` - the one look the frozen design gets. Since 26 Oct 2026 the row tuners are subject to it too: they withhold its days from every score that decides what is served, though not from fitting (*Lockbox period*). Until then they scored the newest draws regardless and only some of them printed a `LOCKBOX WARNING` when their window overlapped it. Then refit on the full window before saving to `data/models/<game>/meta_learner.joblyb` / `meta_learner_v2.joblib` respectively (same persistence convention as `XGBoost.py`).

For games with special columns (Euromillions/EuroDreams/VikingLotto), a **second model per variant** is trained the same way, purely on the special column's own `collect_scores` data (`_special_scores`) and its own number range — determined empirically from the data (`determine_special_range`), since no range is hardcoded anywhere (e.g. Euromillions stars turned out to be 1-12, EuroDreams dream number 1-5, VikingLotto super viking 1-8). Both models of a variant are persisted together in one artifact. `Backtester.backtest(collect_scores=True)` itself mirrors `Helpers.run_model_with_special_column`'s two-call convention (a main-only call, then a special-only call) so the two ranges are never mixed.

**Pick3 uses a positional formulation** instead of being skipped: a per-number ranking cannot express digit order or repeated digits, so for pick3 the candidates are the 30 `(position, digit)` pairs per day. Every pick3-capable base model exposes `score_positions()` - a list of three `{digit: score}` dicts, one per slot, derived from the model's own per-position internals (Markov marginalizes its pair-scored joint, MarkovMonteCarlo tallies its simulated tickets per slot, Poisson uses `1 - exp(-lambda[pos][digit])`, Laplace its discretized per-slot pmf, the per-position XGBoost its per-slot `predict_proba`), normalized per slot at training and serving time (`Helpers.normalize_position_scores`) so the learned weights don't depend on the tuned simulation counts. `Backtester.backtest(collect_scores=True)` records these as `<model>_position_scores` plus `actual_ordered` (the drawn-order truth), one classifier is trained **per position** (all five variants - logistic, gradient boosting, quantum kernel, VQC, classical RBF control), the artifact carries `"positional": True` with `position_models`, and `Predictor.py` serves it as the argmax digit per slot in drawn order (duplicates allowed, never sorted). The same plumbing gives pick3 the classical `MetaLearner`/`MetaLearnerV2` rows for the first time. Held-out reporting for pick3 is per-position top-1 accuracy (chance 0.1) plus the positional ticket's real payout. `runHyperopt.sh` runs this automatically after `HyperoptStatistics.py` and `HyperoptBoost.py`, so the meta-learner is retrained on every fresh hyperopt pass.
